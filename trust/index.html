Institutional Procurement · Sovereign by Design

Ten principles for institutional procurement.

The TEOS stack is designed to pass the questionnaire before the first call. This page documents the ten principles that govern how Elmahrosa International builds, deploys, and supports sovereign AI infrastructure for ministries, hospitals, banks, and enterprises worldwide.

§01
Principle · Customer Perimeter

Sovereign by design, not by configuration.

Customer data, credentials, and code never leave the customer's perimeter. The TEOS stack is engineered so that sovereignty is the default state, not a hardening step. There is no central cloud Elmahrosa operates on a customer's behalf — every product runs inside infrastructure the customer controls.

This architectural decision means that compliance reviews, data protection assessments, and procurement gates do not become integration projects. They become checklists that the deployment topology already satisfies.

Sovereign by design means that, on day one of a deployment, the customer holds every key, every log, every model weight (when local), and every byte of operational telemetry.

What this guarantees
  • No customer data egress to Elmahrosa systems
  • Customer-controlled key custody
  • Single-tenant deployment topology
  • No telemetry phone-home by default

§02
Principle · Explainable AI

Every AI verdict is logged, timestamped, and explainable.

No black-box outcomes. Every decision the TEOS stack makes — every BLOCK, WARN, or ALLOW from Sentinel Shield; every editorial verdict from the AI Engine; every clinical recommendation in UCH — is written to an append-only audit log with the inputs, the rule path, the model version, and the human-readable rationale that produced the outcome.

When a regulator, an internal auditor, or a procurement officer asks why did the AI do that, the answer is in the log, in order, with timestamps.

Audit log contents
  • UTC timestamp + monotonic sequence
  • Input hash (no PII in log surface)
  • Rule path / engine identifier
  • Model + version + verdict
  • Human-readable rationale

§03
Principle · Deployment Topology

Self-hosted, private cloud, or air-gapped.

All TEOS products are deployable inside the customer's perimeter. On-premises, private cloud, or fully air-gapped — whatever the institution's risk model requires. Container images, deployment manifests, and Helm charts are versioned, signed, and reproducible.

Air-gapped operation is a first-class deployment mode, not a degraded fallback. Customers operating in jurisdictions with strict cross-border data rules — Egypt, Saudi Arabia, the UAE, and others — can run the full stack without any external network dependency, provided model weights are pre-stage-loaded.

Supported topologies
  • On-premises (bare metal / VM)
  • Private cloud (AWS / GCP / Azure tenant)
  • Sovereign cloud (regional providers)
  • Air-gapped (no external network)

§04
Principle · Honest Disclosure

Capability claims are tagged, never overclaimed.

Built for the regulatory environments of MENA and East Africa. Every capability claim Elmahrosa publishes is tagged with one of four labels: VERIFIED (we can reproduce it on demand), PROBABLE (we have strong evidence but not a controlled test), INFERRED (we believe it based on architecture or analogues), or SPECULATIVE (forward-looking or aspirational).

This is not a marketing gimmick. It is the protocol Elmahrosa uses internally to keep its commercial and technical statements coherent with the engineering reality. Serious institutional buyers find honest disclosure more commercially persuasive than ambitious claims that crumble under technical due diligence.

Capability labels
  • VERIFIED — reproducible on demand
  • PROBABLE — strong evidence
  • INFERRED — architectural confidence
  • SPECULATIVE — forward-looking

§05
Principle · Pre-execution Defense

AI risk is scored before any action is taken.

TEOS Sentinel Shield runs pre-execution. Every autonomous AI action — every shell command, every file write, every dependency install, every CI/CD step generated by an AI agent — passes through three scan engines and 25 named MCP rules before it is allowed to run.

The verdict is deterministic: BLOCK, WARN, or ALLOW, with a numeric risk score and a human-readable rationale. The verdict is logged. The verdict is replayable. The verdict happens before the action — not in post-mortem cleanup.

Sentinel Shield enforcement
  • 3 scan engines (heuristic, MCP, LLM-assist)
  • 25 named MCP rules
  • Deterministic BLOCK / WARN / ALLOW
  • Numeric risk score per verdict

§06
Principle · Law over Code

AI advises. Humans decide.

Human oversight is enforced at every critical juncture. No TEOS product is permitted to take an irreversible, financially material, or rights-affecting action without a documented human review gate. This is not a UI policy; it is wired into the orchestration layer.

The principle is Law over Code: when a human institutional policy disagrees with the model's recommendation, the policy wins. The model's job is to surface what it knows, score the risk, and route to the right human reviewer — not to act on the institution's behalf without authorization.

Where humans are required
  • Irreversible production writes
  • Financial transactions
  • Clinical recommendations
  • Outbound comms to third parties
  • Any BLOCK / WARN verdict override

§07
Principle · Data Residency & Encryption

Data stays in-region. Keys stay with the customer.

All persistent data — application state, audit logs, model artifacts, embeddings — remains in the customer's chosen region. No cross-border replication, no off-region backups, no implicit data movement to Elmahrosa-managed infrastructure for support purposes.

Encryption at rest is AES-256-GCM with customer-managed keys (CMK) by default. Encryption in transit is TLS 1.3, with mutual TLS where the customer's network allows it. Secrets are referenced through the customer's secret manager — never copied into Elmahrosa-owned vaults.

Encryption defaults
  • At rest: AES-256-GCM, CMK
  • In transit: TLS 1.3, mTLS-capable
  • Secrets via customer secret manager
  • No cross-border replication
VERIFIED CRYPTO
§08
Principle · Vendor Independence

No lock-in by architecture.

Elmahrosa is a Member of the Claude Partner Network, and Claude is the recommended frontier model for TEOS deployments. But the stack is engineered so the customer never owes their continued operation to any single model vendor. Model selection is configuration, not a rewrite.

The orchestration layer abstracts the model provider behind a stable interface. Customers can switch between Claude on AWS Bedrock, Claude on GCP Vertex, Claude on Azure, or a self-hosted alternative without changing application code. Data formats, audit logs, and rule definitions are open and portable.

Portability commitments
  • Cloud-agnostic deployment
  • Model-provider abstraction
  • Open data formats (JSON, Parquet)
  • Exit migration scripts on request

§10
Principle · Procurement Ready

Built to pass institutional due diligence.

The TEOS stack is designed to satisfy institutional procurement gates without bespoke engineering. Standard procurement artifacts — questionnaire responses, SBOMs, dependency graphs, deployment architectures, key-management documentation, and operational runbooks — are available on request under NDA.

Reference deployments and conversations with existing institutional customers can be arranged for serious procurement engagements. Elmahrosa prefers honest references over manufactured case studies.

Available on request

  • Software Bill of Materials (SBOM)
  • Deployment architecture diagrams
  • Key-management & rotation policy
  • Customer references (under NDA)
